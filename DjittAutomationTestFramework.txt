# DJITT Enterprise Automation Testing Framework

The goal is to establish a **reusable testing system that automatically checks every DJITT application before deployment, after deployment, and whenever important functionality changes**.

For DJITT Website Factory, this means testing every generated website, its forms, mobile layouts, integrations, accessibility, security and performance. The same framework should also support the Everyday Financial Confidence website, Genistar-related applications, the DJITT main website, and future client applications.

My recommendation is to build a central **DJITT Quality Engineering Framework** around your existing VS Code + Git + Netlify workflow, rather than adopting a completely separate development platform.

## 1. The recommended technology stack

**Playwright — end-to-end browser testing**

(Core component)

Automates Chromium, Firefox and WebKit browsers. Tests navigation, forms, mobile-sized viewports, user journeys, screenshots and browser errors.

Website: [playwright.dev](https://playwright.dev/)

---

**Vitest — unit and component tests**

Checks JavaScript functions, validation rules, data transformations, pricing calculations and reusable Website Factory components without needing a full browser journey.

Website: [vitest.dev](https://vitest.dev/)

---

**GitHub Actions — automated execution**

Runs the tests whenever code is pushed or a pull request is opened, and can schedule overnight regression tests.

Website: [GitHub Actions documentation](https://docs.github.com/en/actions)

---

**axe-core — accessibility testing**

Detects many common accessibility defects, such as missing accessible names, invalid ARIA usage and insufficient colour contrast.

Website: [axe-core](https://github.com/dequelabs/axe-core)

---

**OWASP ZAP — web security scanning**

Adds automated security checks for authorised test environments. It complements, but does not replace, security reviews and penetration testing.

Website: [OWASP ZAP](https://www.zaproxy.org/)

Additional tools can be introduced for Lighthouse performance audits, dependency vulnerability scanning, visual regression testing and production monitoring. You do not need to install everything on day one.

**Architecture principle:** use one central testing framework with a separate application configuration for each project. Each application retains its own source code, deployment settings, credentials and release controls.


## 2. Establish the architecture before installing anything

Use this structure as the long-term target:

**DJITT Quality Engineering Framework**

Shared test standards, reusable test helpers, policies and reports

**Website Factory**

Templates, generated websites, product catalogues, enquiry forms

**DJITT websites**

SEO, navigation, lead capture, content and accessibility

**Business applications**

User journeys, APIs, CRM integrations and workflows

**Security and reliability**

Dependency checks, permissions, performance and monitoring

**Automated release gate**

Pass → eligible for release · Fail → block release and report defects

The key distinction is that **the framework is shared, but each application has its own tests and acceptance criteria**. An accounting website and a marketplace may share mobile, security and accessibility tests, but their business logic must be tested separately.

Start with the existing `C:\dev\DJITT Website Factory` project as the pilot. Once the framework is reliable, extract common helpers and workflows into a central private repository such as `djitt-quality-engineering`.

## 10. Test integrations without damaging real systems

DJITT applications may connect to Netlify Functions, GoHighLevel, external APIs, email systems and CRM workflows. These require a separate integration-testing strategy.

Use three levels:

1. **Mocked tests:** simulate API success, validation errors, timeouts, rate limits and server failures. These are fast and safe.
2. **Test-environment integration tests:** use dedicated test credentials, a test CRM location or equivalent isolated account, and clearly marked synthetic records.
3. **Controlled live smoke tests:** check essential production paths without creating real customer records, triggering outbound campaigns or changing production data.

For a lead form, test the complete expected journey:

`Visitor → form validation → serverless function → CRM contact → expected outcome`

Verify that authentication failures do not leak credentials, that server errors are handled gracefully, and that repeated requests do not create unintended duplicate contacts.

**Important:** never run destructive tests or automated marketing campaigns against real client records. Do not put API keys, CRM tokens or other secrets in test fixtures, browser code, screenshots or logs. Use GitHub Actions secrets and Netlify environment variables with appropriately limited permissions.

## 13. Add security, accessibility and performance gates

Once browser regression testing is stable, extend the pipeline in separate jobs.

| Gate                | Tool or approach                                             | Release policy                               |
| ------------------- | ------------------------------------------------------------ | -------------------------------------------- |
| Code quality        | ESLint, TypeScript checks where applicable                   | Block on errors                              |
| Dependency security | Dependabot and npm audit, with controlled severity policies  | Block on qualifying vulnerabilities          |
| Secret detection    | GitHub secret scanning or an approved secret scanner         | Block on confirmed secret exposure           |
| Accessibility       | axe-core with Playwright                                     | Block on serious, confirmed violations       |
| Performance         | Lighthouse CI                                                | Set thresholds appropriate to the page type  |
| Visual regression   | Playwright screenshots or a dedicated visual testing service | Review unexplained visual changes            |
| Security scanning   | OWASP ZAP against authorised staging environments            | Block on confirmed release-blocking findings |

Do not make an unfiltered vulnerability scan the sole release decision: establish severity thresholds, review false positives, and track exceptions with owners and expiry dates.

For accessibility, automated checks cannot establish full compliance. Keyboard testing, focus behaviour, screen-reader review and human assessment remain necessary.

For performance, test representative mobile pages under repeatable conditions. A single noisy run should not automatically cause a production rollback; use repeatable measurements and defined budgets.

## 14. Make the framework reusable across every DJITT application

After the Website Factory pilot works, create a private repository named `djitt-quality-engineering`.

Organise the shared repository into:

* `playwright/` — common browser fixtures and utilities.
* `accessibility/` — shared accessibility checks.
* `security/` — standard scanning policies and scripts.
* `workflows/` — reusable GitHub Actions workflows.
* `templates/` — application-specific starter configurations.
* `documentation/` — release policies, test standards and incident procedures.

Each application repository then retains its own:

* Application tests and fixtures.
* Environment-specific base URLs.
* Secret references and deployment configuration.
* Business acceptance criteria.
* Release approvals and exception records.

For the initial rollout, copying a version-controlled starter workflow into each repository is acceptable. As the number of applications grows, move common CI jobs into versioned reusable workflows or a private npm package. Pin dependencies and reusable workflows to reviewed versions so a central change does not unexpectedly break every application.

For AI-powered applications, add tests for retrieval accuracy, incorrect or unsupported answers, prompt-injection resistance, access-control boundaries and sensitive-data leakage. Use fixed evaluation datasets and explicit acceptance criteria rather than assuming an AI response will always be identical.

## 16. Define the release acceptance criteria

Before calling the framework production-ready, require the following:

* [ ] Every application has documented critical user journeys.
* [ ] Critical business workflows have automated regression tests.
* [ ] Required CI checks must pass before a production release.
* [ ] Failures produce useful logs, screenshots or traces.
* [ ] Test and production credentials are separated.
* [ ] No unapproved critical security findings remain open.
* [ ] Accessibility and performance thresholds are documented.
* [ ] Flaky tests are tracked rather than routinely ignored.
* [ ] Production smoke tests run after deployment.
* [ ] A rollback or recovery procedure exists for failed releases.
* [ ] Test results, exceptions and release approvals are auditable.

Build this as a **quality gate in the Website Factory development pipeline**, not as a standalone collection of scripts.

The first priority is the Website Factory because every defect in a reusable template can be reproduced across multiple client sites. Once its templates and generated-site tests are dependable, the same framework can protect every subsequent application you build.

The most useful next step is to inspect the current `C:\dev\DJITT Website Factory` project and tailor the installation to its actual structure. That will avoid overwriting existing scripts, choosing the wrong local server, or building tests that do not exercise your Netlify Functions.

# DJITT.co.uk — Comprehensive Unit Test Plan

A unit test suite for DJITT should verify that the individual pieces of the website work correctly in isolation, before relying on end-to-end smoke tests to prove that the whole system works together.

The distinction is important:

* **Unit tests:** Does a function validate an email correctly, map form fields properly, construct a GHL payload correctly, or handle an API error as expected?
* **Integration tests:** Does the Netlify function communicate correctly with GHL?
* **Smoke tests:** Can a visitor submit an enquiry and see the correct contact, opportunity and workflow outcome in GHL?

For DJITT, I recommend a unit-test suite covering the static website, reusable JavaScript, form validation, routing, Netlify functions, CRM payload construction, error handling and SEO utilities.

The tests should be repeatable, fast, independent of production data and safe to run on every code change.

## 6. Special unit tests for the DJITT–GHL architecture

There are several design decisions that should be tested explicitly.

### A. Contact creation and opportunity creation

Your intended process needs a clearly defined owner for each action.

* If the Netlify function creates only the contact, test that it does not also create an opportunity.
* If the GHL workflow creates the opportunity, test the function's output and separately verify the workflow configuration through integration tests.
* If the function creates both, test partial failures and duplicate prevention for both operations.

**Do not allow both the function and workflow to create the same opportunity unintentionally.**

### B. Correct pipeline and stage

The website enquiry route should use the configured DJITT Website Enquiry pipeline and its intended initial stage, not the Advisor Acquisition pipeline.

Unit tests should verify that pipeline and stage configuration is selected correctly. Tests should not hard-code unverified IDs simply to make assertions pass.

### C. Existing contacts and repeated submissions

Test the business rules for:

* A brand-new contact.
* An existing contact with the same email.
* An existing contact with updated business information.
* A repeated request caused by a browser retry.
* A failed request that is retried.
* Two requests arriving close together.

A unit test can validate the deduplication or idempotency logic, but only an integration test can establish that the live GHL account behaves as intended.

### D. Environment variables

Test missing or invalid values for:

* GHL API token.
* GHL location ID.
* Pipeline ID, if the function uses it.
* Custom-field IDs.
* Other required configuration.

The function should fail clearly rather than silently fall back to another pipeline, location or account.

# DJITT.co.uk — Comprehensive Smoke Test Plan

The purpose of this smoke test is to verify that the current DJITT website rebuild works end to end: visitors can navigate the site, understand the services, submit enquiries, reach the right destination, and enter the correct GoHighLevel (GHL) CRM process.

This should be treated as a **production-readiness test**, not simply a check that the homepage loads.

Based on the current DJITT architecture, the main journey to validate is:

**DJITT.co.uk**

Pages, navigation, offers and calls to action

**Website forms and front doors**

Validation, routing, scoring, resources and bookings

**Netlify and its functions**

Submission handling, field mapping, error handling

**GoHighLevel CRM**

Contact data, route classification, opportunities, pipelines and workflows

**Verified business outcome**

Correct acknowledgement, follow-up, assignment and traceable results

An important distinction: a successful form submission does not necessarily mean an opportunity was created or the correct workflow ran. Your website form has recently started delivering contacts into GHL, so the CRM handoff deserves particular attention.

## 1. Scope of the smoke test

The test covers nine areas:

* Public website availability and navigation.
* All service and offering pages.
* Calls to action, links, forms and interactive components.

* SEO, indexing, metadata and technical integrity.
* Security, privacy, performance and production monitoring.

## 3. Critical end-to-end test: Website enquiry → GHL

This is the highest-priority test because the website form has recently begun creating contacts in GHL, but the full opportunity and workflow journey still needs to be confirmed.

### Test E01–E10 in this exact order

1. **Prepare a unique test lead.** Use a dedicated test email address and a recognisable business name, such as `DJITT Smoke Test 1810`. Do not use a real prospect or client.
2. **Submit the live website form once.** Capture the submission time, displayed confirmation and any request/reference identifier available.
3. **Check the Netlify function.** Open Netlify → your DJITT site → Cloud compute → Functions → `website-leads-submit`. Inspect the invocation and error logs around the submission time. Netlify documents function logs for production and preview deploys. ([docs.netlify.com][1], [docs.netlify.com][2])
4. **Inspect the GHL contact.** Confirm the correct subaccount, contact identity, email, phone, business information and all applicable custom fields.
5. **Check the routing field.** Confirm `DJITT — Front Door Route` is set to `Website`, rather than blank or another route.
6. **Inspect workflow execution history.** Find `DJITT — Website Enquiry → Acquisition` and establish whether the contact enrolled, which actions ran and whether any action failed. HighLevel's execution logs and enrollment history are designed for this investigation. ([help.gohighlevel.com][3])
7. **Verify the opportunity.** Check that the contact has exactly one opportunity in the intended website enquiry pipeline at `01 — New Lead`.
8. **Verify the rest of the journey.** Check owner assignment, task creation, notifications and follow-up actions, using test-safe recipients and channels.
9. **Repeat with an existing contact.** Submit a controlled update to a test contact already in GHL. Verify the contact is updated and that opportunity creation follows the intended re-entry and duplicate-prevention rules.

### Important pipeline discrepancy to resolve

The intended destination has been identified as the **DJITT Website Enquiry pipeline**, stage `01 — New Lead`. The workflow is named `DJITT — Website Enquiry → Acquisition`.

Do not assume the opportunity is being created in that pipeline merely because the contact exists. Explicitly verify the Create Opportunity action, pipeline ID and stage ID. Also confirm that the workflow does not accidentally route website leads to `DJITT Advisor Acquisition`.

The expected result is one correctly populated contact, one correctly routed opportunity, and the intended workflow execution—without duplicates or unintended messages.

**Keep the CRM tests separate from ordinary browser tests:** mock the GHL API for automated tests, or use dedicated test contacts and controlled workflow settings for live integration tests. Do not let every CI run trigger real SMS, emails or sales tasks.

## 5. Release acceptance criteria

DJITT should be considered ready for release only when the following conditions are met.

| Area         | Minimum acceptance criteria                                           |
| ------------ | --------------------------------------------------------------------- |
| Website      | All critical pages load and navigation works                          |
| Forms        | Valid submissions succeed; invalid submissions fail safely            |
| CRM          | Correct contact data and route fields are present                     |
| Pipeline     | One opportunity reaches the intended pipeline and stage               |
| Workflows    | Correct enrollment and actions are verified in execution history      |
| Integrations | Booking, scoring and resource journeys work as intended               |
| Mobile       | No blocking layout or interaction issues                              |
| SEO          | Important pages are indexable, with valid metadata and canonical URLs |
| Security     | No exposed secrets or critical data-handling issues                   |
| Monitoring   | Failures are visible in logs and recovery procedures are known        |

Any critical failure in form submission, CRM routing, opportunity creation, data security or consent handling should block release until resolved. A blocked test is not a pass.

## 6. Recommended execution order

**Phase 1 — Critical smoke test**

Availability, core navigation, website form, Netlify function, GHL contact, opportunity and workflow execution.

---

**Phase 2 — User journeys**

All eight offerings, mobile layouts, Practice Score, booking calendars, resources and external links.

---

**Phase 3 — Technical assurance**

SEO, accessibility, security, performance, error handling and automated browser coverage.

---

**Phase 4 — Regression testing**

Repeat the critical tests after every material change to the site, Netlify functions, GHL custom fields or workflows.
